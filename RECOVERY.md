# Admin Manual Recovery Runbook

**Internal developer reference — not shipped to schools.**

This document describes the procedure for manually recovering a fully locked-out Admin account (lost both password and recovery code). This is a **paid support action** performed per-school, not part of the product's self-service design.

---

## When to use this

The Admin has lost **both** their password **and** their recovery code. There is no self-service path — this is by design (see `SRS.md` §1.7). The developer must intervene directly against the database.

---

## Prerequisites

- Direct database access (Neon dashboard, `psql`, or `bunx prisma studio`)
- The Admin's user ID or username
- A new password chosen by the school (or generated by the developer)

---

## Procedure

### Step 1 — Find the Admin user

```sql
SELECT id, username, name, "recoveryCodeHash"
FROM "User"
WHERE role = 'ADMIN';
```

Note the `id` value — you'll need it for the next steps.

### Step 2 — Generate a new password hash

The app uses **bcrypt with 12 rounds** (via `bcryptjs`). Generate the hash using the same method the app uses:

```bash
node -e "
const bcrypt = require('bcryptjs');
const hash = bcrypt.hashSync('NEW_PASSWORD_HERE', 12);
console.log(hash);
"
```

Replace `NEW_PASSWORD_HERE` with the actual password. **Do not use a weak password** — this is the school's admin account.

### Step 3 — Generate a new recovery code hash

Generate a 64-character hex recovery code and its bcrypt hash:

```bash
node -e "
const crypto = require('crypto');
const bcrypt = require('bcryptjs');
const code = crypto.randomBytes(32).toString('hex');
const hash = bcrypt.hashSync(code, 12);
console.log('Recovery code (show once to admin):', code);
console.log('Hash to store:', hash);
"
```

Save the plaintext recovery code — you will show it to the school administrator exactly once.

### Step 4 — Update the database

Run these SQL statements in order:

```sql
-- Replace USER_ID, NEW_PASSWORD_HASH, and NEW_CODE_HASH with actual values

-- 1. Update password
UPDATE "User"
SET "passwordHash" = 'NEW_PASSWORD_HASH',
    "updatedAt" = NOW()
WHERE id = 'USER_ID';

-- 2. Invalidate any existing recovery codes
UPDATE "AdminRecoveryCode"
SET "replacedAt" = NOW()
WHERE "userId" = 'USER_ID'
  AND "consumedAt" IS NULL
  AND "replacedAt" IS NULL;

-- 3. Create new recovery code record
INSERT INTO "AdminRecoveryCode" ("id", "userId", "codeHash", "createdAt")
VALUES (gen_random_uuid()::text, 'USER_ID', 'NEW_CODE_HASH', NOW());

-- 4. Update the quick-lookup hash on User
UPDATE "User"
SET "recoveryCodeHash" = 'NEW_CODE_HASH',
    "updatedAt" = NOW()
WHERE id = 'USER_ID';
```

### Step 5 — Verify

```sql
-- Confirm password hash updated
SELECT id, username, "passwordHash" FROM "User" WHERE id = 'USER_ID';

-- Confirm new active recovery code exists
SELECT id, "codeHash", "consumedAt", "replacedAt", "createdAt"
FROM "AdminRecoveryCode"
WHERE "userId" = 'USER_ID'
ORDER BY "createdAt" DESC
LIMIT 1;
```

The recovery code row should have `consumedAt = NULL` and `replacedAt = NULL`.

### Step 6 — Communicate to the school

1. Tell the Admin their new password (through a secure channel).
2. Show them the new recovery code **exactly once** — instruct them to store it securely.
3. Recommend they sign in immediately and change the password to something they remember.
4. Remind them that the recovery code is their only self-service recovery path.

---

## Security notes

- This procedure bypasses all self-service recovery design — it is intentionally friction-heavy.
- Never commit recovery codes, password hashes, or this runbook to a public repository.
- The `RECOVERY.md` file should be in `.gitignore` or kept in a private internal wiki.
- Each step is deliberately manual and database-level — there is no CLI tool, API route, or admin UI for this, by design.
- Log this action in your internal support ticketing system for auditability.
